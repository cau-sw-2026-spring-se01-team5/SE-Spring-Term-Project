# 이슈 관리 시스템 Vision

## 1. Vision 문서 설명

이슈 관리 시스템의 **high-level requirements**과 프로젝트의 전체 방향을 정리한 문서이다.

자세한 유스케이스, 디자인 등 설계 세부 사항은 별도 문서에서 다룬다.

## 2. 프로젝트 방향성

해당 이슈관리 시스템은 개발 팀의 진행 상황과 작업 이슈(버그 수정)을 일관된 프로세스로 등록, 업무 할당, 추적이 가능하도록 돕는다.

1. 협업 효율: 역할별(Admin/PL/Dev/Tester) 권한을 다르게 부여하여 업무 흐름을 끊김 없이 지원
2. 이슈 관리: 이슈 등록, 코멘트 추가, 상세정보 확인, 상태 변경 등을 지원하여 업무 지원
3. 추적 가능성: assignee 값, 이슈 상태, reporter 값 등으로 이슈 브라우즈 및 검색이 가능해야 함
4. 이슈 통계 분석: 일/월 별 이슈 발생 횟수 및 트랜드 등을 표시

### 2.1 기능 방향성

- 이슈의 필수 기능(등록, 검색, 상태 변경)을 우선 완성
- 해결된 이슈 이력을 기반으로 assignee 자동 추천 기능을 추가. 여러 가지 방식을 테스트하며 정확도가 가장 높은 방식 선택
- 통계 분석을 통해 의사결정을 지원

### 2.2 설계 방향

- MVC 패턴을 적용하여 UI ↔ 응용 로직을 분리
- Java를 활용한 2개 이상의 UIToolKit으로 구현

### 2.3 품질 방향

- **영속(persistent) 저장을 통해 시스템을 재시작하여도 일관성을 보장하도록 구현
- 단위 테스트가 가능하도록 시스템 설계

## 3. Stakeholders

1. Admin: 계정/역할 관리
2. PL: Dev/Tester에게 배정, 상태 관리, 이슈 브라우즈
3. Dev: 이슈 배정 받은 후 해결, 관련된 내용 기록
4. **Tester**: 이슈(버그) 등록, 수정된 내용 검증
5. **경영진(Offstage)**: 처리량, 업무 효율, 버그 발생 빈도 등 결과 지표 확인

## 4. High-Level Requirements

### 4.1 기능 요구사항

1. 역할 기반으로 계정 관리(Admin/PL/Dev/Tester)
2. 이슈 브라우즈 및 검색 (예를 들어 assignee 값, 이슈 상태, reporter 값 등)
3.  이슈 등록 (꼭 채워야하는 필드는 Title, Description. reporter 필드는 이슈를 등록한 계정으로, reported date는 등록한 날짜와 시간으로 자동으로 채워짐)
4. 이슈 코멘트 추가
5. 이슈 상세 정보 확인 (이슈의 각 필드와 코멘트 history 확인 가능)
6. 이슈 배정을 포함한 이슈 상태 변경
7. 이슈 통계 분석(일/월 별 이슈 발생 횟수 및 트랜드 등 표시)
8. 해결된(closed/resolved) 이슈 이력을 활용한 assignee 자동 추천 기능

### 4.2 비기능 요구사항

1. 영속성: 시스템을 재시작하여도 데이터 유지
2. 확장성: 저장소, UI 교체가 용이해야 함
3. 테스트 용이성
4. 사용성
