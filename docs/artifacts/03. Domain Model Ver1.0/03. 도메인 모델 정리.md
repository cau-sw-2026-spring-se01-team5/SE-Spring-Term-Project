# Domain Model 정리리

## 1) 고민했던 사항
1. Admin, PL, dev, Tester를 하나로 합치지 않은 이유
 - 각 역할 별로 role이 다르므로 분리
2. 이슈에서 코멘트는 속성에 넣지 말고 따로 Class를 만들어 줌
3. Admin이 Project를 만들 때 PL, dev, tester을 지정해준다고 했으므로 Project에 속하지 않은 PL, dev, tester은 없다고 가정
4. 하나의 이슈는 한 명의 PL, dev, tester만 연관된다고 가정

## 2) Conceptual Object

- `Project`
- `Admin`
- `PL`
- `dev`
- `tester`
- `Issue`
- `Comment`

### 2.2 주요 기능

하기에 충분히 설명되지 않은 조건 및 세부 명세 등에 대해서는 각자 적절한 가정을 세우고 프로젝트 문서에서 해당 가정을 명시할 것
1.  **계정** 추가 (계정 종류에는 **admin, PL, dev, tester**가 있음)

2.  **이슈** 등록 (꼭 채워야하는 필드는 Title, Description. reporter 필드는 이슈를 등록한 계정으로, reported date는 등록한 날짜와 시간으로 자동으로 채워짐)

3. 이슈 브라우즈 및 검색 (예를 들어 assignee 값, 이슈 상태, reporter 값 등)

4. 이슈 **코멘트** 추가

5. 이슈 상세 정보 확인 (이슈의 각 필드와 코멘트 history 확인 가능)

6. 이슈 배정을 포함한 이슈 상태 변경

7. 이슈 통계 분석(일/월 별 이슈 발생 횟수 및 트랜드 등 표시)

8. 해결된(closed/resolved) 이슈 이력을 활용한 assignee 자동 추천 기능

### 2.2 예제 시나리오

> 데모를 위해 최소 admin, PL1, PL2, dev1~10, tester1~5 계정을 만들어 둘 것
> 
1. Admin이 **project1**을 추가함. 또한 PL계정, 개발자 계정, 테스터 계정을 추가함.

다음은 모두 project1에 대한 활동임.

1. tester1이 이슈를 하나 생성
→ 해당 이슈의 코멘트를 하나 추가함
→ 시스템은 해당 이슈의 상태를 new로 변경하고, reporter의 값은 tester1으로 저장
2. PL1은 모든 이슈들을 브라우즈 함 
→ 이후 new 상태의 이슈들을 검색
→ 위에서 tester1이 reporter로 되어 있는 이슈에 대해 dev1을 담당자(assignee)로 지정 
→ 코멘트에 적절한 메시지를 추가함
→ 이후 시스템은 해당 이슈의 상태를 assigned로 변경함
3. dev1은 이슈 검색 기능으로 자신에게 assign 되어 있는 이슈들을 브라우즈 
→ 이슈들에 대해 남겨진 코멘트를 포함하여 다양한 정보를 확인하고
→ 코드를 고친 후 코멘트를 추가한 후 해당 이슈를 fixed로 바꿈.
→ 해당 이슈의 fixer는 dev1으로 등록됨.
4. tester1은 자신이 report하였던 이슈 중에 fixed된 이슈들을 검색
→ 적절히 고쳐진 이슈들을 선택하여 “resolved” 상태로 바꿈.
5. PL1은 resolved 상태인 이슈들을 선택해서 closed로 바꿈.
6. optional 기능 (추가 배점): PL2는 현재 new 상태인 이슈들을 브라우즈하고, 상세 정보 보기 기능을 통해 특정 이슈의 상세한 내용과 기존 코멘트들을 살펴봄. 이때 시스템은 fixed된 이슈들의 이력을 이용해서 가정 적절한 개발자를 추천해줌. (예를 들어 “best candidate: dev2, dev5, dev1 등으로”, 가장 가능성이 높은 후보 3명을 순서대로 추천함)

### 2.3 이슈 필드 및 assignee 추천 관련

이슈 필드 (최소이며, 필요에 따라 필드를 추가할 수 있고, 프로젝트 문서에서 설명할 것)

◼ Issue Title // 버그 제목
◼ Issue Description // 이슈에 대한 설명 버그를 재현할 수 있는 방법
◼ Reporter
◼ Reported Date
◼ Fixer // 수정한 사람 이걸 활용해 나중에 누구한테 할당할지 선택
◼ Assignee // 현재 버그를 담당하고 있는 사람 fix되기 전 비어져 있을 수 있음
◼ 우선순위: blocker/critical/major/minor/trivial (기본값은 major)
◼ 이슈상태: new/assigned/resolved/closed/reopened
◼ Comments (코멘트는 추가되는 순서대로 누적됨. 코멘트 날짜 포함)

◼ PL 계정의 자동 assign 추천 기능: 해결된 이슈들을 활용하여 적절한 assignee를 추천하는 방법은 팀별로 자유롭게 제안할 수 있음. 적절한 주기에 따라 데이터를 한꺼번에 모아서 기계학습 등을 통해 학습모델을 구축하여 추천할 수도 있고, Information Retrieval 방법 등을 이용해서 가장 유사한 내용의 기존 해결된(resolved/closed) 이슈의 fixer를 추천할 수도 있음. 단, 적절한 주기에 따라 동작하는 시스템의 경우, 평가 데모를 위해 수동으로 특정 시점에 학습할 수 있는 기능 (예를 들어 “learn now”) 등을 추가할 것.

가장 간단한 방법: 새로 올라온 버그 리포트가 예전 버그 리포트와 비슷하다면
예전 버그 리포트를 fix한 사람을 배정해준다.
머신러닝, Information Retrieval 등 다양한 방법 사용해도 됨. 잘 고민해봐라
