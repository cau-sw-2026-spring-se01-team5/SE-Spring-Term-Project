# SSD & Operation Contract 작성 고민과 선택 이유

## 1) SSD를 어디까지 상세화할지
- 고민: 유스케이스에는 내부 처리 단서도 일부 포함될 수 있어 SSD에 내부 설계를 넣을지 고민했다.
- 선택: PPT 기준(black box)에 맞춰 Actor-`System` 간 이벤트/응답만 남기고 내부 객체 호출은 배제했다.
- 이유: SSD 목적이 "시스템이 무엇을 하는가"를 외부 관점에서 명확히 하는 것이기 때문이다.

## 2) include/extend를 SSD에 어떻게 반영할지
- 고민: UC8/UC9/UC7 같은 관계를 별도 다이어그램으로 분리할지, 현재 UC SSD에 포함할지 고민했다.
- 선택: 현재 UC의 시나리오 흐름 안에서 메시지 단계에 `(include UCx)`, `(extend UCx)`를 주석처럼 표기했다.
- 이유: 시나리오 순서 보존과 이벤트 추적성을 동시에 확보할 수 있기 때문이다.

## 3) Operation Contract 범위를 어디까지 잡을지
- 고민: 모든 시스템 연산에 대해 계약을 작성하면 과도하고, 너무 줄이면 핵심 상태 변화가 누락될 수 있었다.
- 선택: 상태 변화가 중요하거나 오해 가능성이 큰 연산 중심으로 작성했다.
- 이유: PPT 기준에서 postcondition은 "결과가 불명확할 때 특히 유용"하므로, 핵심 변화 연산을 우선했다.

## 4) Postcondition 문장 문법 선택
- 고민: 한국어로 통일할지, PPT 예시와 동일한 영어 패턴을 유지할지 고민했다.
- 선택: 문장 골격은 PPT 예시와 같은 과거형 관찰 문장(`was created`, `became`, `was associated`)으로 유지했다.
- 이유: "행위 지시"가 아닌 "실행 후 상태 관찰"임을 명확히 드러내기 위해서다.

## 5) 예외 흐름 계약의 표현 방식
- 고민: 실패/거절 흐름에서 "아무 것도 바뀌지 않음"을 어떻게 명시할지 고민했다.
- 선택: `No new ... was created`, `... remained unchanged`, `rejection result was returned` 형태를 사용했다.
- 이유: 예외 처리도 시스템 연산의 결과이므로, 상태 불변/거절 응답을 postcondition으로 명시해야 추적이 가능하다.

## 6) 유스케이스 파일 비수정 원칙
- 고민: 누락된 타입/용어 정합을 맞추려면 원본 UC를 손대고 싶을 수 있었다.
- 선택: 요청사항에 따라 UC 원본은 수정하지 않고, 신규 산출물에서만 보완했다.
- 이유: 요구사항 보존과 변경 이력 분리를 위해 원본/파생 산출물을 분리하는 편이 안전하다.
